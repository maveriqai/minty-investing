## Details

**I.** `.claude/skills/thesis-tracker/SKILL.md` step 2 documents the guard
plainly: before pulling holdings for a real position, read
`data/account_identity.json`, call `kite_gateway.get_profile`, and if the
anchor's `user_id` doesn't match the live session's, **stop** — refuse to
fetch or use holdings data, and say a different Zerodha account is
connected than expected.

Two things are true about this guard, and it's worth keeping them
separate:

- The **anchor's write-once persistence** is real, code-level enforcement —
  `engine/tool_capture.py`'s `capture_path()` returns `None` for any
  `get_profile` call once `ACCOUNT_IDENTITY_FILE` already exists (line
  ~134), covered by `tests/test_engine_tool_capture.py`'s
  `test_capture_path_get_profile_is_write_once` /
  `test_save_tool_result_get_profile_writes_once_then_no_ops`. No model
  turn — thesis-tracker's own `get_profile` call included — can silently
  refresh the anchor to a new account.
- The **compare-and-refuse behavior itself** (actually stopping when the
  live session's `user_id` disagrees with the anchor) is prompt-only —
  there's no code path or test asserting the model actually halts rather
  than proceeding. Same category of gap as the memory-extraction
  confirm-before-write pipeline (issue #23): real in the skill's
  instructions, not structurally guaranteed.

Tried a safe way to live-trigger the second half without a real second
account: back up `data/account_identity.json`, edit its `user_id` to a
fake value, run `thesis-tracker` against a real held symbol with no
existing thesis file (`ASIANPAINT`), observe whether it actually refuses,
then restore the original file byte-for-byte. Got as far as taking the
backup (`data/account_identity.json.bak`, diffed identical, then removed)
— the edit to `data/account_identity.json` itself was **blocked by Claude
Code's own auto-mode permission classifier** before it could execute.

That block is itself a small, real data point: a model-initiated attempt
to alter the identity anchor was stopped at the permission layer, not just
by app-level convention — consistent with the "never overwritten by a
model-initiated tool call" line in `CLAUDE.md`, just enforced one layer up
from where that line describes it (Claude Code's own guardrails, not
`engine/tool_capture.py`, in this particular attempt). It also means this
section still can't be live end-to-end verified without either a genuine
second Zerodha account or a human manually editing the file outside any
agent session — worth leaving as a standing gap in the checklist rather
than one this run could close.
