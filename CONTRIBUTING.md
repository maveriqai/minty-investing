# Contributing

Minty Investing is an early-stage, public repo — this doc exists so
contributors (currently: the maintainer's own future sessions and anyone
else who sends a PR) work from the same conventions instead of re-deriving
them per change.

## Start here

Read `docs/vision.md` before touching anything — problem/audience,
architecture, non-negotiables, and success criteria. `docs/skills.md` is
the per-skill spec companion. `CLAUDE.md` is the standing reference for
day-to-day conventions (layout, testing, guardrails) and should agree with
both vision docs; if it drifts, fix all three together, not just the one
you're looking at.

## Setup

Python 3.12+, [`uv`](https://docs.astral.sh/uv/) for everything:

```bash
uv sync
```

No `.env` file or API keys to configure for Minty itself — Kite
authentication is its own interactive login flow (`kite_gateway`), not a
static credential.

## Code style & checks

```bash
uv run ruff check .
uv run pytest
```

There's no CI yet (tracked as a known gap — see `docs/next-phase-plan.md`
§8), so both of the above are on you to run locally before opening a PR.
Network-gated tests that hit live external APIs are marked
`@pytest.mark.network` and skipped by default; run them deliberately with:

```bash
uv run pytest -m network
```

## Repo layout

- `engine/` — the real, importable package. Owns the agent loop, harness,
  guardrail enforcement, skill loading, tool-call budgeting/capture, and
  the Sources footer.
- `mcp/` — Layer 1 (`kite_gateway`, a read-only proxy in front of
  `mcp.kite.trade`) and Layer 2 (`india_price`, `india_filings`,
  `india_macro`, `india_news`, `india_screener`) MCP servers. One
  directory per server, invoked as a script, never imported as a package.
- `.claude/skills/` — canonical skill source (`SKILL.md` + `scripts/`).
  Edited directly, no build step, no generated view.
- `workspace/` — the one fixed, install-wide, git-ignored workspace. Never
  assume its contents in code that ships.
- `docs/` — product/design docs, living and dated.
- `tests/` — mirrors the above, one `test_*.py` per module.

## Non-negotiable product rules

These are hard constraints, not style preferences — a PR that weakens any
of these gets rejected outright, regardless of how it improves whatever it
was trying to improve. Summarized from `CLAUDE.md`; that file and
`docs/vision.md` §5 are the source of truth if this list and either of
them ever disagree.

- **No order execution, structurally.** The six order-placing/-modifying
  Kite tools (`place_order`, `modify_order`, `cancel_order`,
  `place_gtt_order`, `modify_gtt_order`, `delete_gtt_order`) must never be
  registered in any tool surface the model sees, at more than one layer —
  never add them to the gateway's allow-list, and never rely on a single
  guardrail check to be the only thing stopping them.
- **Deterministic calculation only.** Money figures — returns, P&L,
  allocation %, ratios — are always computed in code (a `run_<script>`
  tool), never inferred or computed by the model. The model narrates
  numbers that already exist; it doesn't produce them.
- **Grounding.** Every numeric claim traces to a real tool result or a
  computed file, never model memory. Don't hand-author or patch a capture
  file — a failed/corrupted/oversized capture is reported as a gap, not
  reconstructed from partial reads.
- **SEBI disclaimer** stays attached (by the engine, automatically) to any
  output that could be read as investment advice. Don't route around it.
- **User data stays local and git-ignored** — `workspace/`,
  `.dev-workspaces/`, `results/`, `data/`, root `notes.md`. Never commit
  them, never assume their contents in code that ships.
- **Skills are curated and hand-authored** — reviewed like any other code
  change, never generated by the model at runtime and kept for reuse.
- **Be polite to data sources.** All NSE/BSE fetching goes through
  cached, rate-limited fetchers with backoff (`mcp/common/`). Never
  hot-loop any exchange or scraped endpoint from a session.

## Adding or editing a skill

- `.claude/skills/<name>/SKILL.md` with Agent Skills frontmatter (`name`,
  `description` as the trigger, optional `expected_outputs`,
  `tool_call_budgets`, `deterministic_scripts`, `stages`) + `scripts/`.
- Any ranking/flagging/math logic goes in a typed `run_<script>` SDK tool
  (`engine/skill_tools.py`) shelling out to `.claude/skills/<name>/
  scripts/*.py` — never raw Bash, never model-computed money figures.
- Only declare `stages` (splitting a skill into several fresh sessions via
  `engine/staged_skills.py`) when call volume actually scales with the
  user's own data — portfolio size, holding count. Most skills don't need
  it.
- Write the `SKILL.md` prose for the model reading it at trigger time, not
  as a design doc — trim backstory, keep the steps.

## Adding or editing an MCP server

- One directory per server under `mcp/`, single-file `server.py` using
  `FastMCP`, tools registered explicitly at the bottom (keeps them
  importable in tests via `importlib.util.spec_from_file_location`).
- Docstrings are the tool contract — write them for the model: when to use
  the tool, the return shape, and any caveat about the underlying source's
  reliability.
- Shared fetch/cache/rate-limit code goes in `mcp/common/`, never
  duplicated per server.
- Every tool returns a `{"source", "as_of", "data"}` envelope.
- Symbols/sectors are plain arguments — broker-agnostic by convention,
  never a Kite-specific shape.

## Commit and PR conventions

- Reference an issue where one exists (`Fix #N: ...` is the convention
  already in this repo's history).
- Stage files by exact name — never `git add -A` or `git add .`.
- Prefer a new commit over amending; never amend a commit that's already
  pushed.
- Keep PRs scoped to one change. A bug fix doesn't need surrounding
  cleanup bundled in.

## Known gaps

Check `docs/next-phase-plan.md` §8 and the README's "Known gaps" section
before assuming something is solid — as of this writing that list includes
no Windows support (an `os.fchmod` blocker in `kite_gateway`'s session
persistence), an untested reminder backend, no CI, and issue #23 (the
memory-extraction staging pipeline's confirm-before-write guarantee is
prompt-only, not code-enforced). If your change touches one of these,
raise it explicitly rather than building on top of an assumption that it
already works.

## Security and secrets

Never commit `workspace/`, `.dev-workspaces/`, `data/account_identity.json`,
or any Kite session file — all git-ignored for a reason. "Local-first"
here means the user's holdings, positions, and research stay on their own
disk; don't add code that sends any of it to a third-party service beyond
the data sources this project already calls (Kite, yfinance, NSE/BSE,
Screener.in).
